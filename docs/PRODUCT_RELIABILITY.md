# Sentinel Product Reliability

Sentinel Product Reliability turns release/update/self-observation concerns into explicit evidence rather than hidden product behavior.

## Scope

This foundation deliberately integrates with the existing native product instead of adding another top-level lens:

- **Machine** remains the place for local hardware/runtime context.
- **Sentinel Self Health** is appended to Machine as a separate product-self-observation surface.
- **Update Intelligence** is appended beside Self Health and remains manual/read-only.
- **Task Center** represents the bounded update metadata request as indeterminate work because there is no meaningful percentage to report.
- **Release Trust Manifest** is generated by the packaging pipeline, not inferred by the frontend.

## Update Intelligence

`GET /api/update/status?channel=stable|beta`

The backend reads public release metadata from the Sentinel GitHub repository with a bounded request. It reports current/latest version information and the presence of DMG/checksum assets.

It does **not**:

- download an update;
- replace Sentinel.app;
- execute downloaded code;
- install a package;
- silently check on Machine-page load;
- treat a GitHub release page or checksum as proof of Apple distribution trust.

Stable selection also rejects releases whose tag/name visibly contains beta, alpha, preview, prerelease, or release-candidate markers even if the GitHub `prerelease` boolean was configured incorrectly.

This is an intentional precursor to a future cryptographically authenticated updater. A future automatic updater must have a separate design review covering signed feed metadata, artifact authentication, downgrade/rollback policy, recovery, explicit channel changes, and fail-closed installation.

## Sentinel Self Health

`GET /api/self/health`

Current observations include:

- process CPU sample;
- resident memory (RSS);
- Go heap allocation/reservation;
- total Go runtime memory;
- goroutine count;
- completed garbage collections;
- process uptime;
- self-health collection duration.

Engineering budgets are currently displayed as:

- idle CPU target: **≤ 1%**;
- normal monitoring CPU target: **≤ 3%**.

These are product engineering budgets, not Mac health thresholds. One sample never establishes a sustained regression. Future regression decisions should use retained repeated measurements and controlled workload tests.

## Release Trust Manifest

Development/Beta packaging emits:

`dist/Sentinel-<version>-<channel>.release-trust.json`

Production packaging emits:

`dist/Sentinel-<version>.release-trust.json`

The production manifest is created **only after** the exact DMG has passed the existing fail-closed chain:

1. clean committed source;
2. source SHA stamped into the app;
3. native arm64/x86_64 capabilities present;
4. Developer ID signing with Hardened Runtime;
5. app and DMG signature verification;
6. Apple notarization;
7. stapling and staple validation;
8. Sentinel's exact-artifact release verifier, including Gatekeeper and mounted-app checks;
9. SHA-256 generation.

Only then may the production manifest report signing/notarization/stapling/Gatekeeper fields as `true`.

Beta/development manifests explicitly report those fields as `false`. A manifest describes evidence; it does not upgrade the trust level of the artifact it describes.

## Existing history/change engines and next integration

Sentinel already has bounded history and change primitives, including resource history, storage history, network history, Behavior/Trust history, FSEvents-backed change observation on macOS, and global/grouped timelines. The next engineering phase should unify those existing stores into a coherent **Evidence History / What Changed?** product surface instead of creating a parallel history subsystem.

Target integration sequence:

`observe → retain bounded evidence → correlate by time/object → explain with uncertainty → Workbench review`

Any long-term retention must remain bounded, local, inspectable, and removable by the user.
