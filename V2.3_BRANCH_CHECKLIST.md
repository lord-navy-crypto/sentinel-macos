## Cross-cutting requirements

- [ ] No new permanent-delete path
- [ ] All mutation remains explicit and reversible
- [ ] Every new long-running operation supports cancellation or a strict timeout
- [ ] Every historical collection has a bound/retention policy
- [ ] Every derived result retains evidence provenance
- [ ] Missing evidence is surfaced as limited visibility
- [ ] No score is presented as malware probability
- [ ] No cloud dependency is required for core Sentinel functionality
- [ ] New schemas have explicit version numbers
- [ ] v2.2 state remains recoverable before migration
- [ ] Release documentation matches the actual desktop architecture
- [ ] System Console never exposes arbitrary shell, arbitrary command concatenation, or a web `sudo` terminal
- [ ] System Console mutations never bypass Safe Action preview/confirmation/journal/recovery boundaries
- [ ] Continue Investigation never mutates the investigated object
- [ ] Investigation branching remains bounded and exposes truncation/visibility limits

## Branch gates

### Gate A — data contracts

Do not begin broad UI wiring until incident v2, timeline, storage snapshot, reason-code, migration, System Console, and Continue Investigation object/evidence contracts are stable.

### Gate B — backend complete

P0 APIs must have unit/contract tests before the new P0 UI is considered complete.

### Gate C — feature complete

All P0 items complete. No new P0 features after `v2.3.0-beta.1`; only fixes and bounded P1 work.

### Gate D — release candidate

At `v2.3.0-rc.1`, freeze new features and accept only defects, regressions, documentation fixes, and release blockers.

### Gate E — stable

`v2.3.0` is cut only after branch comparison, regression review, state-migration validation, and final user validation. Merge to `main` remains a separate explicit decision.
